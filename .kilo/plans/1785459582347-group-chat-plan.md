# Group Chat Feature Implementation Plan

## Goal
Enable multiple Characters to participate in a single conversation thread with one User, while preserving backward compatibility with existing 1:1 chats.

---

## Current Architecture (baseline)

```
chats: { id, character_id, character_name, character_avatar, bound_user_id, ... }
messages: { id, chat_id, role: 'user'|'assistant', content, timestamp }
  └── index: chat_id
  └── 'assistant' = single character per chat, avatar/name from chat record
```

Group chat must reuse the same `chats` + `messages` stores. No new tables.

---

## Data Model Changes

### `chats` table — add two fields

| Field | Type | Default | Meaning |
|-------|------|---------|---------|
| `is_group` | boolean | `false` | Existing chats are 1:1. Group chats set this to `true`. |
| `member_ids` | string[] | `[]` | For 1:1: `[character_id]`. For group: all participating character IDs. |

### `messages` table — add one field

| Field | Type | Default | Meaning |
|-------|------|---------|---------|
| `speaker_character_id` | string \| null | `null` | `null` = user message. Set to character ID when `role='assistant'` in group mode. |

No other schema changes.

### Migration
`chats` and `messages` are object stores with no versioned migration yet. Add defaults in `ChatsDB.create()` and `MessagesDB.create()`. Old records will have `undefined` for new fields — code must treat `undefined` as falsy.

---

## Response Strategy (key design decision)

**Recommendation: Broadcast-parallel, sequential rendering**

```
User sends message
    │
    ▼
write user message → messages DB
    │
    ▼
for each member in member_ids (in fixed order)
    │
    ├─ show "X is typing..." bubble (lightweight placeholder)
    ├─ parallel API call: buildMessages with this character's context
    ├─ stream response → replace placeholder with final bubble
    │   bubble carries: this character's avatar + name
    └─ append to messages DB (role='assistant', speaker_character_id=memberId)
```

**Rationale:**
- Parallel API calls reduce wait time vs sequential
- Sequential UI rendering keeps chat readable (one bubble appears at a time)
- Fixed member order ensures deterministic output

**Group size limit:** Enforce max 4 members at group creation. Enough for variety, small enough to avoid context explosion.

---

## LLM Context Per Responding Member

Each character responds with their own isolated context, but shares conversation history:

```
System: [shared world info, forbidden list]
System: [Alice: personality + scenario + speech_style]
User messages + assistant history (all speakers)
User: <new message>
```

**Token budget note:** If user passes `characterId` to `buildMessages`, it loads that character's `characterData` + linked user data. In group mode, each parallel call passes a different `characterId`. Shared system messages (world info, forbidden) can be pre-fetched and passed to avoid N repeated DB reads.

## UI Changes

### 1. Header (`chat.js` renderChat)

**1:1 mode (unchanged):**
```
[←] Alice  [⋯]
```

**Group mode:**
```
[←] Group Chat   [⋯]
[A][B][C]+1  ← stacked avatars with +N overflow
```

Implementation: read `currentChat.is_group` and `currentChat.member_ids`, fetch character data, render stacked avatars.

### 2. Message Bubbles (`createKakaoBubble` in components.js)

Current signature: `createKakaoBubble(role, content, avatar, name)`

Change: add optional `characterId` parameter. If provided and role is 'assistant', look up speaker's avatar/name from that character. If not provided, fall back to `currentChat.character_avatar/name` (1:1 behavior).

Group bubble rendering:
```
[A] Alice
    ┌──────────────────┐
    │ 回應文字         │
    └──────────────────┘

[B] Bob  
    ┌──────────────────┐
    │ 回應文字         │
    └──────────────────┘
```

### 3. Typing Indicator

In group mode, show **per-character** typing placeholder:
```
[Alice Avatar] Alice is typing...
```

Replace placeholder bubble with final bubble when streaming completes for that character.

In 1:1 mode, reuse existing single `streamingBubble`.

### 4. Group Management

Add a "Participants" section in the side menu (visible when `is_group`):
- List members with avatars
- "Add member" → opens character picker bottom sheet
- "Remove" button per member (disabled if only 1 member left)

Participants stored as `member_ids: string[]`. The "owner" concept is unnecessary for v1 — any group member can add/remove.

## API Changes (`api.js`)

### New method: `groupStream`

```javascript
async groupStream(chatId, userMessage, memberCharacterIds, callbacks)
```

**Behavior:**
1. Fetch shared data once: messages, world info, settings
2. For each `memberCharacterId`:
   - Call internal `_streamForCharacter(chatId, userMessage, memberCharacterId, sharedData, callbacks[memberId])`
3. Each per-character stream runs in parallel via `Promise.allSettled`

**Signature change to existing `stream`:**
Add optional 6th param `options = {}` with `options.characterId` override. If provided, `buildMessages` uses that character's data instead of `chat.character_id`. This lets `groupStream` reuse the same streaming logic.

```javascript
// Existing callers unaffected (options is undefined)
APIClient.stream(chatId, userMessage, onChunk, onComplete, onError)

// New group usage
APIClient.stream(chatId, userMessage, onChunk, onComplete, onError, { characterId: 'c1' })
```

### New method: `groupBuildMessages`

Same as `buildMessages` but accepts `characterId` override. Extracted so group callers can pre-build the message array for each character without streaming.

## Creation Flow

### Option A: New "Group Chat" button on chat list (`index.js`)

- Adds button in header actions
- Opens bottom sheet with character multi-select
- Creates chat with `is_group: true`, `member_ids: selectedIds[]`
- Navigates to `/chat/{id}`

### Option B: Convert existing 1:1 chat to group

- In chat side menu: "Add to group" option
- Appends new member to `member_ids`
- Sets `is_group: true`

**Recommendation:** Implement A first, skip B for v1 (users can create a new group).

---

## Creating a Group Chat — Step by Step

1. User taps new group button → multi-select sheet with all Characters
2. User selects 2-4 characters → taps "Create"
3. `ChatsDB.create({ is_group: true, member_ids: [...], character_name: 'Group', character_avatar: '' })`
4. Navigate to `/chat/{newId}`
5. In `renderChat`, detect `is_group` and render group header + member-aware bubbles
6. First message trigger: optionally send a system-generated " introductions " prompt, or let user type first

---

## Edge Cases

| Edge case | Resolution |
|-----------|-----------|
| Only 1 member in group | Allow it. Behaves like 1:1 but with group UI. |
| Member deleted from CharactersDB | Filter out missing IDs at render time. Store `speaker_character_id` in message, resolve avatar at render. |
| API fails for one member | Other members' responses still appear. Show error toast for failed member only. |
| User sends message while characters are still responding | Queue new response cycle — disable send until all members finish current round. |
| Context window overflow | If per-character prompt exceeds model limit, truncate conversation history (same logic existing app uses for single chat). |
| Existing 1:1 chats | No migration needed. New fields default to falsy. Code checks `currentChat.is_group` to branch. |

## Rollout Order

1. **DB layer** — schema-safe defaults, no data migration
2. **API layer** — `groupStream` + `options.characterId` in existing stream
3. **Chat list** — new group creation flow
4. **Chat renderer** — group mode header, group bubbles, parallel response logic
5. **Group management** — add/remove members in settings

Each step independently testable by creating a group and observing responses.

---

## Validation

- [ ] Create group with 2-3 characters → all respond to user message
- [ ] Each response has correct avatar + name
- [ ] Responses appear in member order
- [ ] 1:1 chat still works unchanged
- [ ] Send message while response pending → send disabled until all respond
- [ ] One character's API failure → others still respond, toast shown
- [ ] Open old conversation → no errors (new fields undefined)

---

## Out of Scope (v1)

- @mention selective responses
- Character "presence" / idle status
- Group media attachments
- Character voting / reaction to other character's messages
- Scoped memories per character within a group
